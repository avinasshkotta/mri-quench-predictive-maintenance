# Interview Q&A — QuenchGuard

**How to use this.** These are the questions a reviewer actually asks about this repo, and every answer is meant to be given the same way: open the code, name the file and the function (or line), read the number out of the report that produced it, and only then explain the trade-off. Nothing here is a memorised claim — if an answer says 0.64 false pages per magnet-month, that number comes from `reports/metrics.json → results.lstm.alerts.false_per_magnet_month`, and if it is not in a report the answer points at the report instead of guessing. The pattern to practise is "claim, artifact, trade-off": state the decision, show where it lives, then say what it costs. When you get a question you did not prepare for, say so, then walk the same path — `README.md` for the story, `src/quenchguard/` for the mechanism, `reports/*.json` for the evidence. Answer from code, name the file/line, and finish with "here's the code."

## 1. Problem framing and metrics

### Q1. Why these four metrics — PR-AUC, event recall, false pages, cost — instead of one headline score?

Because each one fails in a different way and the business constraint is not a ranking problem. PR-AUC (0.998 for the LSTM in `reports/metrics.json`) says the scores separate pre-quench windows from normal ones; event recall at ≥ 72 h (100 %, 4/4) says the warning actually arrives inside the service-planning window; false pages per magnet-month (0.64 against a budget of 1.0) says the alert volume is tolerable for clinical staff; and the cost model (`evaluate.cost_summary`) converts misses, planned repairs and wasted visits into dollars ($452,000 net saving on the test period). A single score would let one dimension hide another — a model can have great PR-AUC and still page three days late. The four together encode the actual decision: warn early enough, rarely enough, and cheaply enough. The trade-off is that none of them is comparable across datasets, which is exactly why the C-MAPSS validation reports its own 30-cycle/15-cycle analogues instead of reusing the MRI numbers.

### Q2. Why not accuracy, and how imbalanced is the data really?

Accuracy is dominated by the negative class and hides the only error that matters. The test split has 7,699 windows with prevalence 0.1995, and the LSTM's accuracy is 0.9905 — but the logistic baseline also looks respectable at 0.9318 while catching only 2 of 4 events in time (`reports/metrics.json → results.logreg.events`). A model that never pages would still score about 80 % accuracy here and prevent zero quenches. The imbalance is handled rather than ignored: `lstm.train_lstm` computes `pos_weight = clip((1 - prevalence) / prevalence, 1, 40)` so the positive class is up-weighted but capped, and the window confusion matrix (tn 6091, fp 72, fn 1, tp 1535) shows the operating point is deliberately recall-biased. Accuracy is logged for completeness, never used to select a model or a threshold.

### Q3. How was the operating threshold chosen, and why freeze it?

It was chosen on validation only, under a tightened false-page budget, and then frozen before the test split was scored once. `evaluate.choose_threshold` takes the sweep from `evaluate.sweep_thresholds`, keeps only operating points with `false_per_magnet_month <= 1.0 × 0.6`, and among those maximises in-time event recall, then F1, then threshold. That produced 0.9 for the LSTM ("best lead-time recall among 20 operating points" in `reports/metrics.json → config.threshold_reason`) and 0.993844 for the HistGBDT, each recorded with its reason string. Freezing matters because a threshold tuned while looking at test results is just test-set leakage with extra steps; the 0.6 safety factor exists because the validation slice is small and the test period is later in time. The cost of freezing is an operating point that may be slightly conservative for a new site — which is why `PREDICTION_THRESHOLD` exists as an ops override with its own audit trail.

### Q4. Event recall versus window recall — which one is the release gate?

Event recall is the gate; window recall is a diagnostic. `evaluate.match_events` collapses consecutive positive windows into one alert episode (`evaluate.alert_episodes`), then asks whether that episode overlaps the 96 h horizon before a real quench and whether the clamped lead time is ≥ 72 h. That is the unit the hospital cares about: "was the failure warned about", not "what fraction of 15-minute rows lit up". Window recall still matters as a smoke signal — `fairness._window_recall_by_magnet` warns below 0.90 and fails below 0.50 — and MRI-05 sits at 0.9974 with full event recall, which is the normal pattern of a brief gap between windows. The trade-off is statistical power: with 4 test events, event recall is 4 coin flips, so the policy requires 100 % on every event-bearing magnet rather than averaging, and the audit is honest that it can detect gross under-protection, not small gaps.

### Q5. Why label at 96 h if you only accept 72 h of lead time?

The 24 h of slack is what lets the model learn the early trend instead of the terminal collapse. `labeling.add_labels` marks a window positive when the quench falls inside `(t, t + 96 h]`; `evaluate.match_events` then accepts an alert only if its clamped lead is ≥ 72 h. If the label horizon were also 72 h, every positive window would sit in the last three days, where — per the sensor table in `README.md` — the cold-head threshold only crosses at about 27 h and the RF dropouts appear around 24 h. The longer label window gives the LSTM positive examples during the slow helium-pressure and vibration ramps (≈ 79 h and 44–84 h respectively), which is where the three-day warning actually comes from. The price is a harder target: the model must distinguish "will fail within four days" from "will fail within three", and the early-alert clamping in `match_events` keeps the reported lead honest when an episode starts before the horizon.

## 2. Data and features

### Q6. What does the medallion architecture buy you, and where do Great Expectations run?

It buys a reproducible chain from untouched simulator output to a model-ready table, with a gate between every layer. Bronze is `data/raw`, append-only; `medallion.build_silver` cleans, types, deduplicates and range-filters each stream; `medallion.build_gold` calls `features.build_features` to produce the 36-column frame. The gate is `quality.run_silver_suite`, which builds a Great Expectations suite per table (nulls, physics ranges, enum values, compound-key uniqueness, row-count bounds) and raises `QualityGateError`, aborting the build before bad data is written. Gold is then the only thing the model sees, so a schema or range break fails loudly at the boundary instead of silently shifting the model's inputs. The cost is rigidity: a legitimately new sensor range needs a suite edit in the same commit, which is also the point — the change is reviewable.

### Q7. How do lineage hashes work as an audit trail?

Every layer writes a manifest into `data/lineage/` containing file checksums, row and column counts, schema and upstream links. `medallion._file_record` computes `sha256` per file (and byte size); `medallion._write_lineage` assembles the layer manifest and records which upstream files it was built from. That makes "which bytes produced this gold table" answerable from the repository, and a rebuild that changes an input hash without a code change is immediately visible. It is the evidence behind EU AI Act Art. 10/11 in `docs/eu_ai_act.md`, and `tests/test_medallion.py` verifies checksum checking and the gold-layer invariants. The honest gap is that this is not DVC: there is no remote object store or data-pipeline DAG, just the guarantee that a commit identifies its inputs (`docs/mlops_alignment.md` gap 1).

### Q8. How is causality actually enforced in the features?

By making every statistic look backwards, then testing that truncating the future cannot change it. `features.py` uses pandas rolling defaults (trailing only), `diff()` for pressure and temperature deltas, and `window_end_of` to map a minute stamp to `(t - 15 min, t]`, so everything inside a row precedes its label. The subtle one is the 7-day slope: `_causal_daily_slope` averages by calendar day, rolls 7 days with `min_periods=3`, and then `.shift(1)` so the in-progress day is never used; the join is shifted by one day for the same reason. Missing values are forward-filled within a magnet and then zero-filled — never back-filled, because that would pull the future into a magnet's first rows. `tests/test_features.py` and the horizon-invariance test in `tests/test_labeling.py` are the executable version of the claim.

### Q9. What is the 7-day embargo and why is it there?

For seven days after a quench the magnet is offline for repair, so those windows are not representative of anything the model will score in service. `labeling.add_labels` flags `is_offline` for `window_end` in `[event_time, event_time + 7 days)` and sets `eligible = ~is_offline`; `sequences.prepare_data` filters to eligible rows before splitting and windowing. Without it, the model would learn the dead-magnet signal — near-zero pressure, no RF, no vibration ramp — and could then treat "offline" as a positive class. The embargo also prevents the first days of the next operating period from being labelled by the previous event's tail. The trade-off is fewer training rows on a 90-day study, which is part of why 4 test events is the honest denominator.

### Q10. What are the 36 features, and what does something like `v_rms_rollmax_1h` mean?

The 36 are 10 helium-pressure, 10 cold-head, 8 vibration and 8 RF features, defined in `features.FEATURE_GROUPS` and documented for humans in `features.FEATURE_DOCS`. `v_rms_rollmax_1h` is the maximum vibration RMS over the last four 15-minute windows — a trailing one-hour max, built by `_rolling(s, 4, "max")` in `features._vibration_features`. It exists because a single window's RMS is noisy while the fault is a sustained rise toward the 120 Hz resonance; the trailing max keeps the ramp visible without looking ahead. It is also the top global SHAP feature (mean |SHAP| 1.872) and the top local factor in the recorded case (+7.865, "increases risk"), so it is a good one to be able to explain cold. The eight vibration features are deliberately redundant in this way — level, one-hour max, one-hour spread, spectral peak, resonance band, fault band, ratio, and fault-band mean — because the model, not a hand-written rule, decides which view of the ramp is useful.

## 3. Model

### Q11. Why an LSTM rather than XGBoost — and why is a HistGBDT still in the repo?

The failure signals are staggered across four sensors on different time-scales, so the model needs to fuse trends over hours, not classify one row. The LSTM reads 48 consecutive 15-minute steps × 36 features (`lstm.LSTMDetector`, 2 layers, hidden 64, dropout 0.30) and predicts from the last hidden state, which is exactly the "12 h of context, will it fail in 96 h" question. A tree on the last window sees a snapshot: it can learn thresholds on `p_roll30_mean` or `v_rms_rollmax_1h`, but it cannot represent "pressure is falling while vibration is rising and RF is dropping out" as a sequence. The repo keeps the HistGBDT (`baselines.train_baselines`) for two honest reasons: it is the must-beat baseline (PR-AUC 0.997, 100 % in-time event recall, 0.96 false pages/magnet-month, $450,000), and it is the model SHAP can explain exactly at serving time. The LSTM wins on false pages (0.64 vs 0.96) and slightly on savings ($452k vs $450k), not on ranking — which is the interesting result, and the reason the README reports all three models rather than only the winner.

### Q12. Why 48 steps of 15 minutes?

Because 48 × 15 min = 12 h is long enough to contain the pressure and vibration trend but short enough to stay inside one label horizon and one split. The window is set in `config.WindowConfig` (`seq_len=48`, `step_minutes=15`) and built by `sequences._build_sequences`, which keeps a sequence only if the timestamps are contiguous (`(t[-1] - t[0]) == 47 × 15 min`) and all 48 rows carry the same split code. Contiguity matters because a gap means the model is reading an interrupted history; same-split matters because a window straddling train and test would leak the boundary. Twelve hours is also a practical latency budget: the scoring job runs every 15 minutes (`scores_per_day = 96` in `config.ThresholdConfig`), so a prediction is always available before the next window closes. The trade-off is that a slower degradation than 12 h is only visible through the engineered trend features, not through the raw sequence.

### Q13. Walk me through the training loop.

`lstm.train_lstm` sets the seed, resolves the device, computes the capped positive weight, and trains with `BCEWithLogitsLoss`, AdamW (lr 1e-3, weight decay 1e-4), cosine annealing and gradient clipping at 1.0. Each epoch shuffles the training sequences, steps the optimizer, then scores the validation split and records train loss, validation PR-AUC, ROC-AUC and learning rate into `history`. Early stopping is on validation PR-AUC with `patience=5` and a 1e-4 improvement margin, and the best state dict is restored at the end — the returned model is the best epoch, not the last. The recorded run stopped at 10 epochs with best validation PR-AUC 0.9947 (`reports/metrics.json → training`). Validation PR-AUC, not loss, is the stopping signal because the decision is a ranking-then-threshold problem and loss can improve while the ranking does not.

### Q14. Are the probabilities calibrated? Can I read 0.90 as a 90 % risk?

No, and the repo says so rather than implying otherwise. `lstm.LSTMDetector.forward` returns a logit and serving applies `sigmoid`; there is no Platt scaling or isotonic step anywhere in `lstm.py` or `serving.py`, and no Brier score or expected calibration error in `reports/metrics.json`. The notebook lists isotonic calibration on validation as an explicit next step (`scripts/build_notebook.py`), which is the honest position: the number is a ranking score whose threshold 0.9 was chosen for a false-page budget, not a probability of failure. The practical consequence is that an operator should read "above threshold, here are the top three factors", not "90 % chance of quench this week". If a regulator or clinician needs risk communication, calibration is a prerequisite, not a nice-to-have.

### Q15. How honest is the synthetic-data claim, and what does C-MAPSS actually add?

The MRI data is simulated by `data_gen.py`: 6 magnets over 90 days, 1-minute pressure and cold-head streams, 15-minute vibration and RF windows, 9 labelled quench events plus hard negatives (refills, service visits, near-miss leaks). The physics parameters are plausible and documented in `config.PhysicsConfig`, but nothing here is clinically validated, and the model card states that real-site fine-tuning and a prospective silent trial are required. C-MAPSS adds evidence about the *method*, not the weights: the same causal rolling features, engine-grouped split and false-alert-budgeted threshold reach PR-AUC 0.892, 84 % event recall (21/25 observable engines), 75 % in-time recall at ≥ 15 cycles (12/16 evaluable) and 0.18 false alerts per engine on NASA's official test set (`reports/external_validation.json`). The denominators 25 and 16 are the honest part — 75 engines are right-censored and 9 had already passed the deadline — and `docs/external_validation.md` says plainly that this is not a model-transfer claim and applies no dollar model. The generalisation gap is also reported: validation PR-AUC 0.962 → test 0.892 and in-time recall 100 % → 75 %.

## 4. Explainability

### Q16. Global versus local SHAP — what does each one answer?

Global SHAP answers "what drives this model across the fleet"; local SHAP answers "why this window scored the way it did". `explain.explain_case` computes a SHAP matrix over the test rows with `shap.TreeExplainer`, saves a beeswarm for the global view, and a waterfall for one case; the global table is the mean absolute SHAP per feature, where `v_rms_rollmax_1h` leads at 1.872, then `p_roll30_mean` at 0.565 and `v_rms` at 0.452 (`reports/metrics.json → shap.global_importance`). Local values are the same matrix indexed by row, and `explain.top_factors` turns one row into the top-k payload the API returns. The distinction matters because a feature can be globally important and locally irrelevant for a given alert — and an operator contesting an alert needs the local answer, not the average. Both are explanations of the HistGBDT, which is a caveat covered in Q18.

### Q17. Why SHAP rather than LIME or Grad-CAM?

Because the model being explained is a tree ensemble, and the course rule is "choose by model type". `shap.TreeExplainer` is exact and fast for `HistGradientBoostingClassifier`, and it gives one additive value per feature, so global and local views are the same object aggregated differently. LIME would fit a stochastic local surrogate around a model that is already fully inspectable — extra noise, no extra regulatory value. Grad-CAM needs a convolutional feature map and an image; this input is a 48 × 36 tabular sequence, so there is no spatial map to weight. The LSTM gets gradient attribution instead (`lstm.gradient_importance`), because SHAP over 48 × 36 windows is orders of magnitude slower for no additional decision value — that trade-off is written down in `docs/mlops_alignment.md` §4 rather than left as an omission.

### Q18. What do the top-3 factors in `/predict` actually mean?

They mean "the three features that most moved the *baseline tree model's* score for the last row of this window", not "the LSTM's reasons". `serving.Artifacts.predict` scores the LSTM on the scaled 48 × 36 window, then calls the HistGBDT on `xs[-1:]` (the last scaled row) and runs `explain.top_factors` on that SHAP row with k=3 (`serving.py`). The response makes the provenance explicit: it includes `baseline_probability` and `explanation_model: "hist_gbdt (TreeExplainer)"`, so the client is not misled into thinking these are sequence attributions. The `direction` field is just the sign of the SHAP value ("increases risk" / "decreases risk"), and the magnitude is in the tree model's log-odds space — `expected_value` is −6.904935 in the recorded case. This is the honest version of "explainable AI at the point of decision": a stable, exact explanation from a sibling model that must agree with the champion closely enough to be useful (PR-AUC 0.997 vs 0.998).

### Q19. What is the SHAP efficiency property, and how is it tested?

Efficiency means the base value plus the sum of a row's SHAP contributions equals that row's model output — the explanation is not an approximation that can drift from the prediction. `explain.shap_matrix` returns `(expected_value, shap_values)` from the same explainer, and `tests/test_explain.py` asserts the identity along with top-factor ordering and direction, per the Phase B test description in `README.md`. For a tree ensemble this holds exactly, which is why it is a useful contract: if a refactor breaks the explainer or the feature order, the test fails instead of quietly shipping plausible-looking attributions. The practical limit is that the identity is in log-odds space and applies to the HistGBDT, not to the LSTM's probabilities. For the LSTM, `lstm.gradient_importance` uses mean |gradient × input| on standardised inputs — comparable across features, but not additive and not a SHAP guarantee.

## 5. Fairness and governance

### Q20. Demographic parity versus equalized odds — define both in this setting.

Demographic parity asks whether the alert rate is the same across groups, regardless of outcome; equalized odds asks whether true-positive and false-positive rates are the same across groups, which is a stronger and outcome-aware condition. In `fairness.py`, `demographic_parity_difference` and `equalized_odds_difference` are computed by Fairlearn over all six magnets (`fairness.audit_verdict`, lines around 167–181), and the report stores DPD 0.4387 and EOD 1.0 next to the policy metrics. The group here is `magnet_id` — the only grouping in the study — and the harness takes any column, so vendor, install year or site is a schema change rather than a code change. The important framing is that "selection" in this domain is an alert, and an alert is a benefit only for a magnet that is actually going to fail; for a healthy magnet, silence is the correct outcome, which is why raw parity is the wrong lens (Q21).

### Q21. Raw DPD is 0.4387 and EOD is 1.0. Why does the audit still pass?

Because those numbers are computed over all magnets, including two that have no events and correctly never alert — and averaging over them penalises the model for being right. `reports/fairness.json` shows MRI-03 and MRI-04 with selection rate 0.0, TPR 0.0 and 1,681 windows each; their true-positive rate is undefined in substance (no positives) but enters the Fairlearn calculation as zero, which alone produces an EOD of 1.0 and inflates DPD. The deployed policy is different and is stated in the same file: event recall must be 1.0 on every event-bearing magnet (MRI-01/02/05/06 are all 1.0), selection-rate difference among *alerting* magnets must be ≤ 0.20 (measured 0.1256), ratio ≤ 3.0 (1.4014), and FPR spread across the fleet ≤ 0.10 (0.0657). All pass, so the verdict is `pass`, and `parity_scope_note` explains that DPD/EOD span all magnets while the policy metrics span alerting magnets only. The residual risk is sample size: 4 test events can reveal gross under-protection, not small per-group gaps.

### Q22. Map EU AI Act Articles 10, 11, 12, 13, 14 and 15 to artifacts.

Article 10 (data governance) is the medallion plus Great Expectations plus the sha256 lineage manifests plus the fairness audit — `medallion.py`, `quality.py`, `data/lineage/`, `reports/fairness.json`. Article 11 (documentation) is `docs/model_card.md`, which is attached to every MLflow run by `tracking.log_run`, while Article 12 (logging) is the per-prediction JSONL record written by `serving.append_prediction_log` plus MLflow runs, lineage and ticket files. Article 13 (transparency) is the SHAP top-3 in every `/predict` response and the model card's intended-use/out-of-scope section, and Article 14 (human oversight) is the LangGraph `interrupt()` before `create_ticket` in `agent.py` — not a prompt instruction. Article 15 (accuracy, robustness, cybersecurity) is the PSI drift check with its retraining trigger, Pydantic shape/NaN rejection at the API, and pinned dependencies. `docs/eu_ai_act.md` classifies the system as limited-risk (not an MDR device, not Annex III) and implements the high-risk control set voluntarily — "classify honestly, then over-control" — while Article 43 conformity assessment is explicitly out of scope for a capstone.

### Q23. What exactly is in the Article 12 audit record?

One JSON line per scored window, written by `serving.append_prediction_log` under a lock, with write failures downgraded to warnings so logging can never break a prediction. The record contains the UTC timestamp, magnet id, `sha256` of the raw float64 input window, the LSTM probability, the alert boolean, the threshold in force, the HistGBDT `baseline_probability`, the top-3 SHAP factors (feature and value), and the model name, source (`local`/`registry`), version and latency (`serving.py`). The raw-input hash makes the record reproducible against a specific telemetry payload without storing the payload itself, which is a reasonable privacy/retention trade-off for sensor data. It is on by default to `reports/prediction_log.jsonl`, relocatable with `PREDICTION_LOG_PATH`, and disableable with `PREDICTION_LOG=off` — the tests assert both the record and the off switch. Approved tickets add a second, human-readable record in `reports/tickets/*.md` with "approved by: human operator (HITL gate)" and the UTC creation time.

### Q24. How is human oversight enforced rather than just promised?

By putting the interrupt in the graph, before the write, so no prompt can route around it. `agent.build_graph` creates a `ticket_gate` node; `route` sends any message containing a `create_ticket` tool call there instead of to the tool node, and `ticket_gate_node` calls `interrupt()` with the call id, arguments and a question before invoking `TICKET_TOOL` (`agent.py`). Approval executes the write and returns a `[APPROVED by human operator]` tool message; rejection returns a `[REJECTED ...]` message, states that no ticket was created, and tells the model not to retry without new evidence. The detector itself only alerts — it never dispatches a technician — so the human decision point is the ticket, not the prediction. `tests/test_agent.py` asserts both the interrupt and the filesystem invariant (no ticket file exists before approval), and the offline eval re-checks it as scenario `ticket_with_human_rejection` (interrupted true, ticket output matches the decision). The residual gap is human-factors testing of the approval UI, which `docs/eu_ai_act.md` lists as not performed.

## 6. MLOps and deployment

### Q25. How do you prevent training-serving skew?

By making the service accept the same raw features the gold layer produces, and applying the training transformation server-side. `POST /predict` takes one unscaled 48 × 36 window; `serving.Artifacts.predict` wraps it in a DataFrame with the frozen `feature_names` and transforms it with the persisted training `StandardScaler` (`serving.py`). Feature order is frozen in `features.FEATURE_COLUMNS` and stored in the model payload's `meta`, so the service and the pipeline cannot silently disagree about column order; `/model-info` publishes the names, sequence length and threshold for verification. The API rejects anything that is not exactly 48 × 36 and rejects NaN/infinite values with 422 before scoring, so a shape change fails loudly. Drift monitoring runs on the same 36 columns, which catches distribution movement but not a silent semantic change (for example, a vibration RMS now computed over 2 kHz) — that is risk R7 in `docs/eu_ai_act.md`, and the reason windowing is documented as part of the model contract.

### Q26. How does the MLflow registry work, what happens if it is down, and which knobs stay configuration?

`tracking.log_run` logs params, every quoted metric, artifacts (including the model card) and the serving triple, registers the LSTM as `quenchguard_lstm`, and moves the `champion` alias to the new version. Serving selects the artifact origin with `MODEL_SOURCE`: `local` reads `models/` (what the container ships), `registry` calls `serving._registry_triple`, which resolves `@champion`, downloads that run's `serving/` directory and reports the version. If the registry is unreachable, the exception is caught, a warning is emitted, `source` falls back to `local`, and `fallback_reason` is exposed in `/model-info` — a tracking outage never takes scoring down. The same philosophy applies to logging: `log_run` returns `None` on failure and the pipeline continues, because a 3-minute training run should not die because MLflow is unhappy. The operational knobs follow the same rule — `PREDICTION_THRESHOLD` overrides the frozen threshold (with `_resolve_threshold` warning on a non-numeric value), `PREDICTION_LOG`/`PREDICTION_LOG_PATH` control the audit log, and every override lands in the audit record — so a site can retune operations without a rebuild. Rollback is alias movement, not a redeploy — the previous version stays addressable — and the trade-off is configuration drift, which is why `docs/mlops_alignment.md` admits there is no separate staging environment.

### Q27. PSI versus KS — and what exactly makes retraining fire?

PSI is a binned measure of how far a feature's distribution has moved, and the repo uses it because the policy is written in effect-size terms: PSI > 0.2 is the alert line in the model card. `monitoring._drift_snapshot` runs Evidently's `DataDriftPreset(num_method="psi", threshold=0.2)` between the train split and the current batch, then `monitoring.drift_verdict` applies two rules: any of the top-8 SHAP features has drifted, or more than 25 % of all features have drifted. KS was not chosen or implemented; it is a two-sample test that becomes significant with large n even for trivial differences, and it does not give the "how much has the population moved" reading the retraining policy needs, so there is no claim here about how it would behave. The current run recommends retraining because key features drifted — `p_roll30_mean` 1.561, `p_roll5_mean` 1.542, `p_mean` 1.534, `v_rms_rollmax_1h` 0.253, `v_rms` 0.230 — while `drifted_share` is exactly 0.25, which does *not* exceed the 0.25 share rule (`reports/drift.json`). That distinction matters in an interview: the trigger is the key-feature clause, not the fleet-wide share clause, and `scripts/monitor.py --check` exits non-zero so CI can enforce it.

### Q28. Why one container on one machine — no EC2, no autoscaling — and what about cold starts?

Because everything in the serving path is small, CPU-only and already committed, so a full cloud instance would be operational surface with no benefit. The image builds the Next.js static export and the FastAPI app with CPU torch; `models/` (the LSTM, scaler and HistGBDT, about 0.6 MB) and `frontend/` are committed, so no GPU, pipeline run or data regeneration is needed to start (`README.md`). `fly.toml` describes one `[[vm]]` with `shared-cpu-1x / 1 GB`, `auto_stop_machines = "stop"` and `min_machines_running = 0`, which is roughly $6.70/month always-on. One process is not only a cost choice: `build_graph` defaults to `MemorySaver()`, so checkpoints and a pending ticket approval live in process memory, and a second replica would strand the approval queue — the 409 "approval pending" path in `webui._repair_thread` assumes the same process can see the thread. Cold starts are the price: after auto-stop, the first request pays container boot, torch import, artifact load, and the first `doc_search` TF-IDF fit (the index is cached per process), which is why the health check has a 20 s grace period. At real fleet scale the answer changes: a managed container service, a shared checkpointer (Postgres/Redis) instead of `MemorySaver`, and warm minimum capacity.

## 7. LLM, RAG, agent and MCP

### Q29. How does RAG keep the agent grounded?

The agent may only cite what a tool returned, and documentation is a tool like any other. `agent._chunk_markdown` splits the model card, case study and README at `##` boundaries into ~1,200-character chunks; `agent._rag_index` fits a TF-IDF matrix once per process; `agent.doc_search` returns the top-k chunks with source, heading, text and cosine score. The system prompt's rule 1 is "investigate before recommending" and rule 4 is "never invent sensor numbers: everything must come from a tool result", so a numerical claim without a preceding `score_magnet` or `sensor_summary` call is a contract violation the eval can catch. The offline harness checks `evidence_precedes_answer` for the investigate scenario and `score_payload_contract` / `sensor_payload_contract` against the real model and data (`reports/agent_eval.json`), which is stronger than checking that the answer "sounds right". RAGAS faithfulness (0.75) is the statistical backstop, not the primary mechanism.

### Q30. TF-IDF versus embeddings and a vector database — why this choice?

Because the corpus is three markdown files, the demo must run offline and deterministically, and CI must not need an API key or a service. `TfidfVectorizer(stop_words="english", sublinear_tf=True, ngram_range=(1, 2))` plus cosine similarity is exact, reproducible, free, and fast enough that rebuilding at process start is invisible next to loading torch. The trade-off is real: lexical matching misses paraphrase and synonymy, so a question phrased as "cryogen boil-off" may not retrieve a chunk that says "helium pressure", and there is no semantic ranking or cross-encoder rerank. The index is also per process and rebuilt at start, with no scheduled re-index job (`docs/mlops_alignment.md` gaps 4 and 7). The upgrade path is deliberately shaped as a drop-in: swap the vectorizer for an embedding model and the matrix for a vector store behind the same `doc_search(query, k)` signature, then re-run the same eval and add context recall.

### Q31. Describe the agent's tool loop and the routing decision.

It is a LangGraph `StateGraph` with an `agent` node, a `tools` node and a `ticket_gate` node, wired `START → agent`, `agent → route`, and `tools`/`ticket_gate → agent`. `route` inspects the last message's `tool_calls`: no calls → `END`, any call named `create_ticket` → `ticket_gate`, otherwise → `tools` (a prebuilt `ToolNode` over `fleet_risk`, `score_magnet`, `sensor_summary`, `doc_search`). State is a message list with the `add_messages` reducer, so tool results are appended and the model sees them on the next turn; the default recursion limit bounds runaway loops, and a rejection message explicitly says not to re-create the ticket without new evidence. That design addresses three of the nine documented failure modes directly: wrong tool chosen (explicit descriptions plus conditional routing), outdated output (tools read the live model and silver layer, not training-time memory), and repetitive loops (recursion limit plus the rejection instruction). The rest are mapped in `docs/mlops_alignment.md` §3.

### Q32. How does the HITL interrupt work mechanically, including resume?

`interrupt()` raises a LangGraph pause inside `ticket_gate_node` and returns the human decision when the graph is resumed. `run_agent` invokes with `Command(resume=...)` and the same `thread_id`, which is how the `MemorySaver` checkpoint is found; the web UI streams an `interrupt` SSE event and a `halted` event, then offers Approve/Reject. On approval the node calls `TICKET_TOOL.invoke(call["args"])`, which writes `reports/tickets/<stamp>_<magnet>.md` and then attempts the SMTP notification in a `try/except` so a mail outage cannot lose the ticket. On rejection it returns a tool message containing the reason and the instruction not to retry, so the model's next answer summarises the rejection instead of re-drafting. If the browser tries to send a new message while an approval is pending, `webui._repair_thread` raises 409 rather than silently starting a second thread. The full invariant is tested at three levels: unit tests, the filesystem assertion in the eval harness, and the `ticket_with_human_approval`/`ticket_with_human_rejection` scenarios in `reports/agent_eval.json`.

### Q33. How do you contain prompt injection and the other agent failure modes?

Layered, and mostly by removing capability rather than by asking the model nicely. The system prompt scopes the agent to MRI magnet maintenance and instructs it to refuse clinical advice and unrelated tasks; retrieved document text is treated as untrusted input; the tool set is an explicit allow-list; and crucially there is no free-text write path — `create_ticket` takes a magnet id, a priority that must be one of low/medium/high/critical, a summary and one action, and anything else is rejected by `agent.create_ticket`. The nine failure modes are enumerated with their mitigations in `docs/mlops_alignment.md` §3: hallucination (RAG + "never invent sensor numbers" + RAGAS), wrong tool (descriptions + routing), outdated output (live tools), injection (guardrail + allow-list), conflicting agents (single orchestrator, no multi-agent handoff), forgetting context (`MemorySaver` keyed by `thread_id`), repetitive loops (recursion limit + rejection feedback), context overload (k=3 chunks, tool results truncated to 1,500 chars in the API), and debuggability (opt-in LangSmith, SSE tool trace, structured eval). The honest limit: the guardrail is prompt-level, so it is a soft control for *language* behaviour and a hard control only for *actions*, because actions are gated by code.

### Q34. MCP exposes only read-only tools — how is that enforced, and what happens to an aborted SSE stream?

`mcp_server.py` registers exactly four tools — `fleet_risk`, `score_magnet`, `sensor_summary`, `doc_search` — as thin wrappers over the agent functions, and deliberately does not import or register `create_ticket`; the module docstring and the server instructions both state that ticket creation requires a human approver and is unavailable over MCP. `tests/test_mcp.py` asserts the advertised set, that the write tool is unreachable, that every tool has a description for LLM discovery, and that `doc_search` returns ranked citations. The value versus bespoke integrations is discovery plus one interface: any MCP client (stdio, SSE or streamable HTTP) gets the same schemas and descriptions instead of a hand-written HTTP client per consumer. On the streaming side, an aborted browser connection can stop the graph between `agent` and `tools`, leaving an `AIMessage` with unanswered `tool_calls`; `webui._repair_thread` reads the checkpoint, refuses with 409 if an approval is pending, and otherwise appends `[CANCELLED by the user before execution]` tool messages so the next turn does not get rejected by OpenAI for an unanswered tool call. That repair is covered by `tests/test_webui.py`.

## 8. LLMOps and cost

### Q35. How does the token ledger work, and why strip the dated model snapshot?

`llmops.TokenLedger` records prompt and completion tokens per call and prices them against a per-1M-token table; `from_messages` scrapes real usage from `AIMessage.response_metadata["token_usage"]`, so scripted test doubles simply contribute nothing rather than fake costs. `canonical_model` strips a `-YYYY-MM-DD` suffix, so `gpt-4o-mini-2024-07-18` prices at the `gpt-4o-mini` family rate instead of appearing unknown — the response metadata reports the snapshot, the price table is keyed by family. Unknown models are priced at zero *and* listed in `unpriced_models`, so the failure is visible rather than silently free. The committed run is small but real: 2 calls, 1,086 prompt tokens, 68 completion tokens, $0.000204, one model, no unpriced entries (`reports/agent_costs.json`). The ledger is saved to that file so a cost regression is reviewable in a diff, which is the LLMOps equivalent of a performance budget.

### Q36. Retries, timeout and token ceiling — what failure does each one prevent?

They cover three different failure shapes and are all in one factory, `llmops.build_chat_model`. `max_retries=3` lets the OpenAI SDK retry 408/409/429/5xx with exponential backoff, because rate limits at scale are routine rather than exceptional and a single 429 should not fail a maintenance investigation. `timeout=60` bounds a hung call so a stalled upstream cannot hold a request thread forever. `max_tokens` (default 1024, overridable with `LLM_MAX_TOKENS`) caps completion length so a misconfigured or adversarial prompt cannot multiply cost — the prompt side is already bounded by retrieval k=3 and the scope guardrail. Temperature is 0.0, which is a deliberate choice for a safety workflow: the same investigation should produce the same draft. `tests/test_llmops.py` covers the wrapper's retries, timeout and ceiling behaviour, which is how these remain guarantees rather than configuration folklore.

### Q37. RAGAS faithfulness is 0.75 and answer relevancy 0.9001 — what do they mean, and what is the gap?

Faithfulness measures the share of claims in the answer that are supported by the retrieved context; answer relevancy measures how directly the answer addresses the question. The asymmetry is informative: the agent usually answers the question, but roughly a quarter of its claims were not grounded strongly enough by the retrieved chunks in that run, which is exactly the failure a maintenance agent cannot afford (`reports/ragas_scores.json`). Faithfulness is therefore the metric that matters here, and it is reported next to the structural eval rather than instead of it — `reports/agent_eval.json` passes 4/4 scenarios on tool order, payload contracts, the HITL invariant and guardrail refusal. The gaps are stated in `docs/mlops_alignment.md`: context recall is not measured, and there is no production hallucination sampling — RAGAS runs on demand via `scripts/eval_agent.py --ragas`, not on a slice of live traffic, and the eval set is four scenarios. So 0.75 is a release check on a small sample, not a monitoring guarantee.

## 9. Debugging and trade-offs

### Q38. A user says the model gave a wrong answer. How do you debug it?

First separate the three things that can be "wrong": the score, the explanation, or the agent's narrative. For the score, replay the same window through `POST /predict` (determinism is tested) and check `/model-info` for `model_source`, `model_version`, `threshold` and `feature_names`; then read the Art. 12 record for that request — the input `sha256`, probability, threshold, `baseline_probability` and top-3 factors are all there, so you can tell whether the LSTM and the HistGBDT disagreed. If the window itself is suspect, check shape/contiguity and compare the feature values against the gold frame; if the distribution looks off, `reports/drift.json` gives the PSI per feature and may explain a legitimate late-period shift. For the narrative, pull the SSE tool trace or the transcript and compare each claim to the `score_magnet`/`sensor_summary` payload — the `no_tools_on_refusal` and `evidence_precedes_answer` checks in `reports/agent_eval.json` are the same comparison automated. Then reproduce the scenario with `scripts/eval_agent.py` before changing anything, so the fix has a regression test rather than a story.

### Q39. What changes with 10× the data?

More magnets before more days per magnet, because the binding constraint is events per group, not rows. With 10× the events the fairness audit stops being a 4-event smoke test and can report per-group recall with intervals and extend the grouping beyond `magnet_id` to vendor and install year — `fairness.py` already accepts any column. The split discipline has to survive the growth: global time cut-points, contiguous same-split windows and the 7-day embargo all stay, and with more events the embargo and the horizon interact more, so event-aware splitting becomes worth the complexity. Compute is not the issue — a 2-layer, hidden-64 LSTM over 48×36 is small — but window count grows linearly, so training time and the drift reference both grow, and the reference should be windowed (for example, last N months) rather than "all history". C-MAPSS is the cautionary example: adding engines without respecting grouping and censoring inflated nothing but the apparent sample size, which is why `docs/external_validation.md` reports 25 and 16 as denominators rather than 100.

### Q40. What would you change before calling this production-ready, and what gaps remain?

The model needs real-site fine-tuning and a prospective silent trial, not just a better synthetic score; the model card and the AI Act document both say that in the limitations. Probabilities need isotonic calibration on validation (already listed as the next step in the training notebook), so a threshold means something to a clinician. The agent needs a vector store with context-recall measurement, a scheduled re-index, and production hallucination sampling instead of on-demand RAGAS. The platform needs a persistent checkpointer (so approvals survive a restart and more than one replica), a real retraining loop rather than a CI gate plus human promotion, a staging environment, and a certified QMS (ISO 13485 / ISO 42001) plus human-factors testing of the approval UI. Incident workflow tooling is the deployer's responsibility — the evidence trail exists in `reports/metrics.json → results.events` and the ticket files, but the process around it does not. None of these are hidden: they are enumerated in `docs/mlops_alignment.md` §7 and `docs/eu_ai_act.md` §4, which is the point — a stated gap is a plan, an unstated one is a surprise.

## Red flags to avoid

- **Do not call the synthetic results a clinical or operational validation.** They are a methodology demonstration on simulated physics; the honest claim is "the decision framework transfers, evidenced by C-MAPSS", never "this will work in a hospital".
- **Do not present `quench_probability` as a calibrated risk.** There is no calibration step in the repo, and 0.9 is a policy threshold chosen under a false-page budget, not a 90 % chance of failure.
- **Do not say DPD/EOD are the deployed fairness policy.** The policy is event recall = 1.0 per event-bearing magnet plus alerting-only parity and FPR spread; DPD 0.4387 and EOD 1.0 are reported for the Fairlearn contract and are inflated by clean magnets that correctly never alert.
- **Do not quote a metric that is not in `reports/*.json`.** If a number is not in a report, say "see `reports/metrics.json`" and go read it — inventing a percentage in an interview is the fastest way to lose the room.
- **Do not claim SHAP explains the LSTM.** The `/predict` top-3 come from the HistGBDT baseline on the last scaled row; the LSTM's view is gradient attribution, and the response says so via `explanation_model`.
- **Do not claim the agent is autonomous or that MCP can open tickets.** `create_ticket` sits behind `interrupt()` and is deliberately absent from the MCP server; the detector only alerts.
